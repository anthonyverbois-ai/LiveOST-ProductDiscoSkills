# Changelog

All notable changes to this plugin are listed here.

## Unreleased

### Added
- Live view technical choices in `docs/live-view.md`: built with Astryx (Meta's design system), pinned version, packaged as one self-contained file.
- Live view metadata: the run log now records the finish time, the status of each source and the plugin version, and who made each change (agent or squad). They feed the "last refresh" date and the tree changelog of the v0.2 live view, specified in `docs/live-view.md`.
- Repository skeleton: plugin manifest, marketplace entry, contribution guide, pull request and issue templates.
- Draft skills: `ost-setup` (onboarding), `ost-rules`, `daily-run`, `weekly-synthesis`.
- Templates: Notion data model and sources configuration example.
- Change of course: new `ost-change-outcome` skill to re-anchor the tree on a new outcome or north star, with an outcome history, a `parked` status for opportunities and a `paused` status for solutions. The weekly synthesis now flags drift between the evidence and the active outcome.
- Onboarding in two batches: a trial batch on the last month, started after a short volume recap and an explicit go, is used to build and calibrate the first tree; the full history (all time or a chosen start date) is then processed with the rules learned during calibration, again after an explicit go.
- Shipped features check: opportunities are checked against documentation and release notes. A feature that addresses an opportunity becomes a `shipped` solution with its release date, evidence is split before and after the release, and opportunities with no evidence since the release are proposed as `addressed`. The weekly synthesis checks new release notes.
- Notion setup, from a first test: a creation order for the databases (relations and rollups need their targets), a tree view and a solutions board created by the onboarding, and the one manual step (turning on Sub-items) explained to the user. Accounts is now a count of distinct accounts.
- Processing at scale: new `backfill` skill for large volumes (thousands of items): batches of about 100 with a compact tree summary, checkpoints and resume, deduplication by source ID, a consolidation pass for new candidates, attachment confidence and review by sample. Evidence gains `Source ID` and `Confidence`; the daily run skips items already ingested; the weekly synthesis and the live view never load the whole evidence base.
- Squad scope: the onboarding asks for the areas and features the squad owns, what is explicitly out of scope, the segments, and how the scope shows up in the sources; it sets the source filters and documentation sections from it. Evidence about other squads' areas is marked `out of scope`, counted in the recap and kept out of the tree.
- Onboarding tree workspace: the agent asks where in Notion to create the tree, checks the connector can write there, flags who will see the customer verbatims, reuses existing databases instead of duplicating them, and creates them only after confirmation.
- Onboarding progress: the agent shows the whole path at the start, opens and closes each step with its position ("Step 4 of 9"), keeps a progress line of what is done and what comes next, and reports progress during long steps. The change of course follows the same pattern.
- Live view, first version on fictional data (`view/`): the tree numbered by priority (1, 2, 3 for branches, 1.1, 1.2 for sub-opportunities), evidence and account counts that open the verbatims, solutions folded under each opportunity, a filter by feature when the tree covers several, candidates and set-aside opportunities below the tree, links from every item to its Notion page, the daily recap dated with the last run, pending decisions and the tree changelog. Built with Astryx into one self-contained page; a larger test tree (10 branches, 4 features) checks how it holds up.
- Several squads: a PM can follow several squads, each with its own tree (configuration, Notion page and databases, learned rules, live view). Running the onboarding again adds a squad without touching the others; one daily run and one weekly synthesis cover all squads, with one recap and one section per squad; the change of course takes the squad name.
- Building the tree: new `build-tree` skill, used by the onboarding, the change of course and the backfill consolidation. It writes the need behind each piece of evidence, groups needs from the specific up into opportunities and sub-opportunities, tests each opportunity's link to the outcome (no link: proposed as parked), checks shipped features, sizes with quantitative data and gives a first ranking, then shows the tree before writing it.
- Backlog as a source: the onboarding connects the squad's issue tracker, read only. Delivered items count as shipped features; planned and in-progress items are proposed as solutions of the opportunities they address, with a backlog link and a backlog status refreshed by the daily run. The weekly synthesis proposes new links and asks about backlog items with no opportunity and top opportunities with no solution in the backlog.

### Changed
- Reading Notion works on every plan, free included: the plugin and the live view read one database per query, and compute evidence counts, accounts and last-evidence dates themselves instead of reading the rollups, which the Notion connector does not return as values. A grouped count is used when the plan allows it. Rules in "Reading the databases" in `templates/notion-data-model.md`.
- The repository is now `anthonyverbois-ai/LiveOST-ProductDiscoSkills`: the install command and the plugin manifest links point to the new name. The plugin name and its commands (`/live-product-discovery:…`) are unchanged.
- The plugin is now presented as LiveOST: README title, contribution guide and display name. Its technical name and commands (`/live-product-discovery:…`) are unchanged, so existing installs keep working.
