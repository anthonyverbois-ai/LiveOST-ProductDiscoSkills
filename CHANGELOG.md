# Changelog

All notable changes to this plugin are listed here.

## Unreleased

### Added
- Volume per source: the table of sources in Notion and the visual tree show how many items each source of evidence brought since the tree started, and how many of them are within the squad's scope (Total items, In scope). A signal source shows what it counted over its window, and how much of it is mapped to an opportunity. Before, only the items read at the last check were stored, and the page showed a status with no volume.
- Refreshing the tree by asking: when the user asks in a conversation to refresh the tree, the daily run reads what is new in the sources, updates Notion and ends by publishing the visual tree again. `ost-view` alone refreshes the page only.
- The visual tree, delivered: a new `ost-view` skill publishes the page that shows the squad's tree, and refreshes it. The onboarding publishes it once the first tree is written and the quick review happens on it; every daily run and weekly synthesis, a change of course and an undo refresh it; `/live-product-discovery:ost-view` refreshes it on demand. The page is built once, in the repository, and loads the squad's tree from a data file published next to it, so nobody builds anything. It is a copy of the Notion tree: decisions are still taken in Notion, and a page that reads Notion when it opens remains the next step.
- What a tree with no outcome is for: the squad can state it (`focus`). The visual tree shows it at the top; it is never used as an outcome.
- On the page: the prospects, the revenue of the accounts and the signals of each opportunity, the backlog status of a solution, the link to the source of each verbatim, and the evidence of sub-opportunities under their parent. Candidates sit under "Too early to rank", proposed creations under "Waiting for a decision".
- One evaluation case on fictional data: refreshing the visual tree.
- Revenue on each opportunity: a new ARR property holds the total revenue of the customer accounts behind an opportunity's evidence, read from the accounts query, with each account of the data source counted once. It sizes the opportunity next to its accounts and breaks ties; it never enters the score and is never stored per customer. The revenue a source shows on its own record is not used: that record may be one of several through which the customer pays.
- What an account is: the teams of one company are one account; a subsidiary or a member firm named in the evidence is an account of its own, or counts as its group (`account_level`); a group named without its entity is not counted next to one of its named entities; a piece of evidence that names several accounts counts each of them once.
- Delivery statuses for solutions: `planned` and `in delivery` join the statuses of a solution. The plugin writes them for a solution linked to a backlog item, from the tracker's status, through a map agreed during onboarding (`status_map`). The statuses of discovery stay the squad's and are never overwritten. A board of solutions no longer shows the items linked from the backlog under no status.
- Views that read without a manual step: the opportunities are shown in four tabs (Top level, Sub-opportunities grouped by parent, Candidates, All) instead of one flat table sorted by rank, where parents and sub-opportunities mixed until the user turned on Sub-items. Sub-items becomes optional.
- A legend at the top of the tree's page and a description on every Notion property: the squad reads what evidence, need, kind, accounts, prospects, candidate and rank mean where they appear.
- A check after large writes: after a first tree or a backfill, the stored rows are read back and compared with what was meant to be written, before anything is shown.
- A glossary of the squad's features in the extraction context, so that a feature is not taken for another with a close name.
- Two evaluation cases on fictional data: accounts and revenue, and the status of solutions linked to the backlog.
- One evaluation case on fictional data: which opportunities are trending.
- One evaluation case on fictional data: clear needs that no opportunity holds.
- A documentation base the squad already maintains: when the squad keeps its own base (a folder of files, a wiki, a repository gathering the help center, the release notes or the features), the onboarding asks for it and the plugin reads it instead of collecting the documentation again (`via: knowledge-base`). The plugin never rebuilds it and never writes to it, takes the squad's scope and the documentation sections from it when it sorts its pages by feature, and keeps what else it holds in its role (backlog items are delivery; needs the squad already ranked are not customer evidence).
- Age of the documentation: documentation and release notes are read live or from a dated copy the squad refreshes (`freshness: live` or `snapshot`, `max_age_days`, 35 by default). The date is read from the copy itself at each run, never from the configuration. Past the allowed age the source is partial, the summary says how old the copy is, and a check against shipped features says that releases after that date are not in it.
- Partial sources: a source that can only be read in part (a connector that cannot page past its most recent items, for example) can be accepted as partial (`coverage: partial`, with what is missing). Its evidence is attached as usual, its counts are a floor, and it stays partial in the Sources database. A search across every chat is never used to get around it without the squad's agreement.
- A trial of the plugin, or a tree over a fixed period: `history: none` and `runner: none` end the onboarding after the quick review, with no scheduled task.
- A tool with an API and no connector can feed the export folder through a script the user runs (`via: script`), and a signal source keeps its saved query (`query`).
- Two evaluation cases on fictional data: a partial source, and a documentation base past its allowed age.
- Where the agent's autonomy stands: the live view spec gains an "Agent autonomy" panel (what the agent does on its own, what it still proposes with its last 5 decisions per type, what always stays with the squad), and the weekly synthesis says where each type still proposed stands. Neither is a countdown or a progress bar: the panel informs, so that no one accepts proposals just to unlock a type.
- Documentation and release notes can be read from a public website (`via: url`, with the sitemap or the index page) when no connector exists. The onboarding asks to run the scheduled task once by hand before relying on it, and every skill says that `${CLAUDE_PLUGIN_ROOT}` means the repository root when the plugin is read from its repository rather than installed.
- Evaluation suite: `evals/` holds five cases on fictional data (attaching and classifying evidence, duplicates across sources, instructions hidden in a ticket, the ranking formula, solutions in disguise), run with `claude plugin eval .`. Each case checks that the rules were loaded and grades the answer against them. The contribution guide and the pull request checklist ask for it when a skill changes.
- Extraction on a fast model: new `evidence-extractor` agent (model haiku) that extracts and classifies one batch against a compact summary of the tree and returns structured rows; the backfill and the daily run hand it their batches and keep consolidation and synthesis in the main session, and extract themselves when the agent is not available.
- Catch-all check: an opportunity holds one need. Each week, the synthesis reads a sample of the evidence of the opportunities that grew most; when it falls into several distinct needs, it proposes a split with the groups and their evidence.
- Insight platforms as a source: tools that already turn conversations into customer insights (a product feedback tool, a research repository) are read as evidence, with the insight's ID and link. A summary written by the tool or a colleague is kept but flagged and capped at medium confidence; the platform's search finds insights but never counts them; and conversations the platform already covers are read from one place only.
- Counting customers, once: the same need from the same customer reaching several sources (a call, a colleague's note about it, a chat message) is linked as a duplicate and counted once, within a configurable window (3 days by default). Each account gets a type (customer, prospect, internal, unknown): feedback logged under the user's own company is resolved to the customer named in the text, or marked internal; only customer accounts count in Accounts and in the ranking, and prospects are shown apart.
- Weight and use of each source: each source has a weight in the ranking (`rank_weight`, 1 by default; 0 keeps its evidence attached and visible but out of the ranking). A source whose items carry no customer words, such as tickets known only by their category and tags, can be a signal source: it never creates evidence, and its volume per category is written on the opportunities it is mapped to, next to the evidence.
- Kinds of evidence: each piece is classified as a need, a bug or a question when it is extracted. All three attach to opportunities, each opportunity shows its split by kind, the weekly synthesis names the opportunities made mostly of bugs (they may call for fixes more than for discovery), and the configuration can weigh each kind in the ranking.
- Several outcomes, or none yet: a squad that owns several product areas can set one outcome per area, and each top-level opportunity is linked to the outcome it moves most. A squad with no outcome yet can start without one: the tree is ranked on evidence alone, nothing is parked for lack of a link, and the drift check is off until the squad sets an outcome. `ost-change-outcome` now adds, replaces or retires one outcome without touching the others.
- Undo and a record of every change: new `/live-product-discovery:ost-undo` command that reverses a change the agent made on its own (creation, merge, rename, move, re-rank, link, status), moves the evidence back, says what later changes it also affects, and records the undo as a correction. Every structural change, made or proposed, is now a row of a new Changes database (type, status, before, after, evidence moved, reason, run): it feeds the recap, the live view's pending decisions, timeline and tree changelog, and replaces the free-text Changes of the run log.
- Live view technical choices in `docs/live-view.md`: built with Astryx (Meta's design system), pinned version, packaged as one self-contained file.
- Live view metadata: the run log now records the finish time, the status of each source and the plugin version, and who made each change (agent or squad). They feed the "last refresh" date and the tree changelog of the v0.2 live view, specified in `docs/live-view.md`.
- Repository skeleton: plugin manifest, marketplace entry, contribution guide, pull request and issue templates.
- Draft skills: `ost-setup` (onboarding), `ost-rules`, `daily-run`, `weekly-synthesis`.
- Templates: Notion data model and sources configuration example.
- Change of course: new `ost-change-outcome` skill to re-anchor the tree on a new outcome or north star, with an outcome history, a `parked` status for opportunities and a `paused` status for solutions. The weekly synthesis now flags drift between the evidence and the active outcome.
- Onboarding in two batches: a trial batch on the last month, started after a short volume recap and an explicit go, is used to build and calibrate the first tree; the full history (all time or a chosen start date) is then processed with the rules learned during calibration, again after an explicit go.
- Shipped features check: opportunities are checked against documentation and release notes. A feature that addresses an opportunity becomes a `shipped` solution with its release date, evidence is split before and after the release, and opportunities with no evidence since the release are proposed as `addressed`. The weekly synthesis checks new release notes.
- Notion setup, from a first test: a creation order for the databases (relations and rollups need their targets), a tree view and a solutions board created by the onboarding, and the one manual step (turning on Sub-items) explained to the user. Accounts is now a count of distinct accounts.
- Processing at scale: new `backfill` skill for large volumes (thousands of items): batches of about 100 with a compact tree summary, checkpoints and resume, deduplication by source ID, a consolidation pass for new candidates, attachment confidence and review by sample. Evidence gains `Source ID` and `Confidence`; the daily run skips items already ingested; the weekly synthesis and the live view never load the whole evidence base.
- Squad scope: the onboarding asks for the areas and features the squad owns, what is explicitly out of scope, the segments, and how the scope shows up in the sources; it sets the source filters and documentation sections from it. Evidence about other squads' areas is marked `out of scope`, counted in the recap and kept out of the tree.
- Onboarding tree workspace: the agent asks where in Notion to create the tree, checks the connector can write there, flags who will see the customer verbatims, reuses existing databases instead of duplicating them, and creates them only after confirmation.
- Onboarding progress: the agent shows the whole path at the start, opens and closes each step with its position ("Step 4 of 9"), keeps a progress line of what is done and what comes next, and reports progress during long steps. The change of course follows the same pattern.
- Live view, first version on fictional data (`view/`): the tree numbered by priority (1, 2, 3 for branches, 1.1, 1.2 for sub-opportunities), evidence and account counts that open the verbatims, solutions folded under each opportunity, a filter by feature when the tree covers several, candidates and set-aside opportunities below the tree, links from every item to its Notion page, the daily recap dated with the last run, pending decisions and the tree changelog. Built with Astryx into one self-contained page; a larger test tree (10 branches, 4 features) checks how it holds up.
- Several squads: a PM can follow several squads, each with its own tree (configuration, Notion page and databases, learned rules, live view). Running the onboarding again adds a squad without touching the others; one daily run and one weekly synthesis cover all squads, with one recap and one section per squad; the change of course takes the squad name.
- Building the tree: new `build-tree` skill, used by the onboarding, the change of course and the backfill consolidation. It writes the need behind each piece of evidence, groups needs from the specific up into opportunities and sub-opportunities, tests each opportunity's link to the outcome (no link: proposed as parked), checks shipped features, sizes with quantitative data and gives a first ranking, then shows the tree before writing it.
- Backlog as a source: the onboarding connects the squad's issue tracker, read only. Delivered items count as shipped features; planned and in-progress items are proposed as solutions of the opportunities they address, with a backlog link and a backlog status refreshed by the daily run. The weekly synthesis proposes new links and asks about backlog items with no opportunity and top opportunities with no solution in the backlog.
- Freshness of opportunities: a configurable waiting period after a release before proposing `addressed` (8 weeks by default); usage data, when available, holds back that proposal for a little-used feature; partial coverage links a feature to the most specific opportunity; complaints about a shipped feature become a new opportunity instead of reviving the old one; the squad's own solutions are proposed as shipped when they appear in the release notes or the backlog; opportunities without evidence for 24 weeks (configurable) are raised once in the weekly synthesis, never archived by the agent.
- Quantitative data set up at onboarding: one read-only connection to a data warehouse, an analytics tool or an analytics agent (for example MotherDuck or nao). With the user, the agent writes and tests three saved queries (ARR and segment per account, usage of the squad's features, the outcome's metric) and agrees on an account key to match the accounts named in calls and tickets. Sizing, ranking and the adoption check use these queries; revenue weighs in the ranking but never on its own and is reported per opportunity, never per customer; the weekly synthesis reports the outcome's metric.
- Source health: a new Sources database (one row per source: tool, status, last successful read, last check, items read, detail) sits at the top of the tree's page in Notion. Every run updates it; a source that usually returns items and stays silent for 3 working days is marked partial. The live view shows one dot per source next to the recap title and a banner when a source is partial or failed.
- Team chat channels as a source: the onboarding asks for the Slack or Teams channels where colleagues share customer feedback, read only. Each message is read with its whole thread, including new replies to older threads; the evidence keeps the permalink of the exact message or reply, so the Notion card opens it. Feedback relayed by a colleague is always captured and counts like any other evidence (the rationale says it was relayed); a message that names no account is still captured; the colleague's name is not stored; and since these channels cover the whole product, they get no filter at the source: the existing scope check does the filtering, and messages with no customer need are skipped.
- Changing sources: new `/live-product-discovery:ost-change-sources` command to add, replace or remove a squad's source without touching the tree. It connects and tests the new tool, rewrites and tests the saved queries, compares old and new quantitative figures before switching (and asks before any ranking change), resumes evidence where the old tool stopped, avoids duplicates when source IDs change, keeps past evidence and marks the old source as replaced. The daily recap suggests the command when a source has failed for 3 working days.
- File imports and customer contacts: the onboarding accepts CSV and Excel files of customer feedback (survey answers, NPS comments, old exports), even with thousands of rows. The agent shows the columns, agrees the mapping with the user (verbatim, date, account, contact, ID, link, kind), counts useful rows, builds a stable ID per row when there is none, runs the trial batch on the file's last month (or a 200-row sample without dates) and processes the rest in batches. Evidence gains a Contact property (name and email of the customer contact, when the source gives it), used to draft messages to customers for solution discovery; a colleague who relayed feedback is never stored as a contact. `ost-change-sources` imports files added later, keeping only new rows.
- Live view: candidates are decided on their card. The card shows where the agent would place the candidate and why it did not add it on its own; accept, merge with an existing opportunity, set aside or reject, with the tree updating at once and the last decision undoable. Opportunities changed by the agent on its own carry a discreet marker with the reason. When the tree covers several features, each branch shows its feature on its own line ("Feature: Exports").

### Changed
- The recap says only what happened and what waits for the squad. It no longer counts the items read outside the squad's scope, which stay in the run log, and it never adds a line to say that nothing is to decide.
- The period the tree covers is shown on the visual tree and on the tree's page in Notion: from the date its evidence starts (`tree.since`, written by the onboarding) to the last refresh.
- A source the squad accepted as partial no longer raises a warning on the visual tree: it shows as OK with the mention "known limit". The banner is kept for failures and for problems the squad has not accepted.
- On the visual tree, the first block opens with what the tree holds in total (the items in the squad's scope since it started, with the total read on hover), then gives the recap of the last run. Each source of evidence shows its items in scope, and the table of sources in Notion shows the items in scope only. Before, it showed only the last ingestion. The button that showed or hid all the solutions is removed: each opportunity keeps its own foldable solutions.
- Independent by default. The agent now makes structural changes on its own whenever it is sure, from the first day (`autonomy: proactive` is the default), and proposes only when it is not sure or when the decision is the squad's: changing the outcome, parking, splitting, archiving. Earning each type of change through five decisions becomes an option (`autonomy: earned`). A type the squad undoes twice in four weeks still goes back to proposals.
- The tree's page in Notion asks nothing of the squad: the link to the visual tree first, then the opportunities, the solutions and the sources, the unattached evidence marked as needing no action, the legend folded, and the databases at the bottom. There is no list of things to do: what waits for a decision is in the recap and in the visual tree.
- README: "How it works" and its image say that the tree runs on its own, and that the squad steps in only when it wants to: it answers the proposals the agent is not sure about and corrects. Before, the squad's decision read as a required step of every run.
- README: it opens on the problem and the promise, then one image that shows a morning of the agent and the tree it keeps up to date (fictional example). The comparison with one-shot OST generators moves up, with a row on the backlog, and the status moves below what you get.
- README: the design principles say that the agent creates an opportunity on its own for each clear need that none holds.
- README: an up-to-date status, how to get started before the roadmap, one diagram of the loop and one table of commands in place of six paragraphs, and a section on where the data stays.
- On the visual tree, a card shows the customer accounts first and in bold, since they make the rank; evidence, prospects and revenue follow, lighter. The legend says what ranks: customer accounts, with revenue only breaking ties. Before, every count was in bold and evidence came first, so a branch with more evidence and more revenue looked misranked under one with more accounts.
- Trending is a rule, and a narrower one: only ranked opportunities trend, and only customer and unknown accounts and their evidence make a trend. A candidate carried by a few prospects no longer shows as trending. The definition moves to "Ranking" in `ost-rules`.
- Every clear need feeds the tree. When a piece of evidence fits no opportunity and states a clear need, the agent creates the opportunity on its own, as a candidate until it has two accounts, instead of leaving the piece unattached until someone sorts it. Unattached evidence is read again at each run against the tree as it stands. Only pieces too vague to name a need stay unattached, and the recap no longer presents them as something to sort. Creating an opportunity is no longer a type of change the agent has to earn; a squad that prefers to approve each one sets `autonomy_per_type: {create: propose}`.
- Sources are read in pages small enough to be read whole, asking only for what a run uses (text, date, account, ID, link). An answer that comes back cut is read again in smaller pages, never used as it is.
- A parent opportunity counts the evidence of its sub-opportunities with its own (evidence count, accounts, prospects, kinds, ledger, score, revenue) and is recomputed whenever one of them changes. The rule was missing.
- At a first tree or a consolidation, the rationale is written once per opportunity, on its creation row, instead of once per piece of evidence.
- Evidence out of scope is stored without its verbatim: the need in one line, the source and its link are enough, and the squad that owns the area reads the source itself.
- With an accounts query, the query decides the type of an account; the status a source carries is used only when the query cannot match the account.
- Signals: when several categories map to one opportunity, its accounts are counted once across them.
- Fewer questions in the onboarding: the frame is filled in from what the workspace already says (project instructions, a list of features per squad, a documentation base) and the user only corrects it; decisions that do not depend on each other are asked in one round; the agent writes and tests the quantitative queries itself and shows them for confirmation, and skips the outcome query while the squad has no outcome. A private page is offered first for a trial, and the volume of a source with no filter for the squad's scope is given as a total and a sampled estimate, said to be an estimate.
- Proactive agent from the first day: the agent makes structural changes on its own when it is sure (clear evidence, nothing in the learned rules or the squad's past decisions against it, no repeated undo of that type of change) and proposes only otherwise. Creating, merging, renaming, moving, re-ranking, linking shipped features and backlog items, marking solutions shipped and opportunities addressed can be automatic; changing the outcome, parking, splitting, archiving and deleting stay human. Every change is listed in the recap under "Done by the agent" and can be undone. The onboarding's branch-by-branch calibration becomes a quick review of what the agent is unsure of, and the two-week observation mode is gone; `autonomy: propose-only` keeps the previous behaviour.
- Reading Notion works on every plan, free included: the plugin and the live view read one database per query, and compute evidence counts, accounts and last-evidence dates themselves instead of reading the rollups, which the Notion connector does not return as values. A grouped count is used when the plan allows it. Rules in "Reading the databases" in `templates/notion-data-model.md`.
- The repository is now `anthonyverbois-ai/LiveOST-ProductDiscoSkills`: the install command and the plugin manifest links point to the new name. The plugin name and its commands (`/live-product-discovery:…`) are unchanged.
- The plugin is now presented as LiveOST: README title, contribution guide and display name. Its technical name and commands (`/live-product-discovery:…`) are unchanged, so existing installs keep working.
- Configuration and learned rules live in Notion: each squad gets a configuration page (`LiveOST configuration – <squad>`, the configuration as one YAML block) and a Rules database (rule, status, the corrections it comes from, replay result). Runs read everything from Notion, never from local files, and a Notion search finds every squad set up.
- Autonomy is earned, type by type: each type of structural change (create, merge, rename, move, …) is proposed until the squad has accepted, without edits, 4 of its last 5 decisions on that type; then the agent makes it on its own when it is sure. Two undos of a type in 4 weeks send it back to proposals, and the recap says when a type changes. `autonomy: proactive` keeps the agent acting from the first day; `propose-only` is unchanged.
- Ranking follows one written formula: an opportunity's score is the sum of its customer accounts' weights (unknown accounts included) (source weight × kind weight × age × before or after a release); revenue, then recency, break ties; and siblings closer than 5% keep their order. Ranks move only when their inputs move, and the score is written on each opportunity.
- Readable evidence and quieter days: the title of a piece of evidence is now the need behind it, in one line, and the exact verbatim moves to its own text property, so a table of evidence stays readable with long call excerpts. The daily recap is always written to the run log, but the user is notified only when something waits for them (`notify: decisions-only`, the default).
- Re-ranking is no longer a change the agent has to earn: the ranking follows the written formula, so scores and ranks are updated on every run, and `ost-undo` points to the weights instead of undoing a re-rank.
- Consistency sweep: the daily run collects from every source of evidence (not only "calls and tickets"), the recap counts items; a merge sets the absorbed opportunity to `merged`; the Changes types gain `reframe` and `add solution`, and `ost-undo` reverses them; the unused `proposed` evidence status is gone; the Sources list names insights and signals; the stability margin of the ranking is 5% of the higher score; small wording fixes in the onboarding and the README.
- Statuses and terms: a creation awaiting a decision is `proposed`, and `candidate` means only "below two accounts"; the live view shows them apart. A colleague's own product opinion is stored as `internal` evidence everywhere (one rule said to skip it); assumptions no longer get a `paused` status they do not have; the Accounts count is defined once (customers and unknown accounts); Product area and a rule's Outcome are set by the skills that know them; dormant opportunities are asked about once, with the date kept on the opportunity.
- The rule that items are data, never instructions, is the first rule of "Evidence" and is repeated where items are read (daily extraction, backfill batches, the weekly catch-all check), and it covers every source, Notion verbatims included.
- Eval criteria ask only what the rules say: a page-break complaint may be a need or a bug, a crash may stay unattached, and a reframed opportunity is judged on the customer's point of view, not on the first person.
- Autonomy per type: `autonomy_per_type` overrides the global setting for one type, `ost-undo` offers to send a type back to proposals at the first undo, a type needs five decisions before it can become automatic, and the configuration block may be edited by hand (outcomes excepted). The onboarding no longer claims that the quick review has "earned" types.
- The daily recap links every opportunity, change and view it names, drops its empty lines, names the accounts behind a proposal, says the run's duration, and never prints a score ("+3 accounts this week" instead). A change the agent made on its own now triggers the notification: before, a wrong merge on a quiet day waited for Monday.
- Customer contacts are copied into Notion only from the sources the user allows (`keep_contacts`, false by default), asked once at the onboarding with a reminder of who will see the tree.
- Onboarding, as a PM meets it: tags, trackers and documentation sections are listed from the connected tools instead of asked from memory; the outcome's effect on the tree (what gets parked) is said before it is set; a partial source is flagged before the trial batch; the "go" says the duration, that the session must stay open and that the tree is written before the review; the quick review closes the first-tree decision and drafts the rules the full history runs with; the Notion connector's capabilities are probed with a stated fallback for each gap; insight platforms that cover only some conversations are read alongside the source, with duplicates matched by the original's link.
- A change of course pauses the runs while the tree is reviewed, re-evaluates parked opportunities too and lets the squad decide branch by branch; a change of sources asks the new tool's tags afresh, reviews the rules that named the old tool, and offers to rewrite the old evidence's links when the migration kept the IDs. The squad's interview notes are a source of their own.
- The live view spec follows the decisions loop (a card only sets the Changes row; the run applies it). Skill descriptions match what the skills do, the README says the plugin has not yet run on a real squad and lists the later roadmap, and an eval criterion quotes the rule it relies on.

### Fixed
- On the visual tree, opening an opportunity turned the page blank when a shipped solution had no release date in Notion. A date Notion does not hold now shows as nothing, or as "Not known", and never breaks the page; the same goes for the last evidence of an opportunity and the date of a verbatim. Reported in #50.
- The visual tree showed the date of the copy at the top ("Copy of ..."), which read as the date of the tree: a page published again without a run looked refreshed. The badge now shows the last refresh, the end of the last run, with its age in days; the date of the copy moves to the hover text and the footer.
- On the visual tree, the counts of the sub-opportunities shown under a branch did not add up to the count of the branch, with nothing to say why. A branch now says how its evidence splits between its own pieces and those of its sub-opportunities, and a candidate that belongs under a branch is shown there, unnumbered, instead of below the tree.
- From a first daily run on a real squad. Hand edits could not be found by date: the Notion connector filters on the date a row was edited only through a property, and Evidence had none. Evidence gains a Last edited property, and the run reads the edited rows before it writes anything, since its own writes count as edits. A solution linked to a backlog item that left the backlog filter kept an old status: a linked item is now read through its link.
- The onboarding never published the live view the specification promised: no skill said how, and the page only ran on fictional data.
- From a first onboarding on a real squad. The test of a source checks how far it reaches (a second page, or the oldest item of the trial period), not only that it answers: a connector that listed only its most recent conversations passed the test before. The onboarding's progress is kept in a run log entry (step reached, what is waiting on the user), so a new session resumes it: a connector authorised during the conversation may only appear in a new session. The Notion creation order names the relations that can only be added once their target exists (Riskiest assumption, Duplicate of) and the paired property of Evidence and Run log; the status of a source has six separate options; a select option cannot hold a comma. A backfill no longer assumes that a source lists its items oldest first.
- Plugin files are found once the plugin is installed: skills point to the templates and to each other with `${CLAUDE_PLUGIN_ROOT}` and the plugin's skill names (`live-product-discovery:<name>`), instead of paths relative to the user's working folder.
- The onboarding says where the scheduled runs live: a cloud scheduled task by default (runs with the computer off, sees no local file, so the plugin's repository is attached to it), a desktop scheduled task when a source is a local export folder, never a loop tied to the session. The task's prompt lists the squads' configuration pages. A daily run that cannot see an export folder marks it partial.
- Counts are stored on each opportunity: Evidence count, Accounts and Last evidence are plain properties written by the plugin, recomputed only for the opportunities a run touched or a person edited, instead of rollups the connector cannot read. The weekly synthesis and the live view no longer need the whole evidence base. Each piece of evidence also keeps the agent's own choice, so a move made by hand in Notion is detected and logged as a correction.
- Moves made by the agent are no longer read as corrections: Agent choice is a relation to the opportunity (plus an Agent status), and the agent updates it whenever it moves evidence itself (merge, move, undo). Before, it held the opportunity's name, so a rename or a merge by the agent made every piece of evidence look as if a person had moved it, and the weekly synthesis learned rules from the agent's own actions.
- Earned autonomy can start: the first tree's creations are written as rows of the Changes database, and the quick review counts as one decision on creations. The default threshold is 4 accepted out of the last 5 decisions (it was 9 of 10, which a small squad would take months to reach).
- The company's own name (`own_company`) is asked at step 1 of the onboarding, with the squad's name. It was asked inside the quantitative data setup, which a squad without a data warehouse skips, leaving every note logged by a colleague counted as a customer.
- The weekly replay of a draft rule is bounded: its own test cases plus a sample of about 30 past attachments, instead of "past attachments" with no limit, which contradicted the rule never to re-read the whole evidence base.
- Decisions are carried out: a proposal the squad accepts or edits (in Notion or in the live view) is applied by the next daily run, which sets Applied on, updates Agent choice on the evidence moved and lists it in the recap under "Applied". Before, nothing applied an accepted proposal. The weekly synthesis now writes a run log entry like the daily run, and reactivating an addressed opportunity is a recorded change (`reactivate`) that can be undone.
- The ranking can be computed without re-reading the evidence: each opportunity keeps a Ledger (per account, the inputs of its best piece of evidence), updated at every attachment, move or undo; the daily run refreshes scores from it (age weights move with time) and the weekly synthesis writes ranks. The stability margin is a single pass over the previous order, with no previous order at the first ranking; a shipped solution with no known release date lowers no weight; and the `ranking.*`, `trial_days` and `history` keys of the configuration are now read by the rules and the onboarding.
- Onboarding order: the trial batch only extracts and classifies, and the first tree is built once, at step 6, under the first-tree rule (before, the backfill consolidation could build it a second time under the autonomy rule, giving two different first trees from the same data). Feedback files get their Sources row once the database exists, the confirmed signal mapping is written to the configuration and keyed by the opportunity's Notion page, and a change of course rewrites the configuration's outcomes.
- The autonomy counter cannot flip-flop: an undo counts as a decision against, and a type sent back to proposals needs 5 new decisions before it becomes automatic again. The quick review of the first tree counts as one decision on creations, not one per opportunity, so skimming a twelve-opportunity tree no longer earns automatic creations on day one.
- A backfill can resume unattended: the run log entry carries a Status (running, finished, interrupted) and a Checkpoint (last item per source), and a daily run that falls back to batches resumes from them and puts the review by sample in its recap instead of waiting for someone.
- The Ledger can be scored at any date: it keeps, per account and per static weight (source × kind), the latest date of evidence carrying it, and the age and release weights are applied at score time; before, it froze the "best" piece and the before-or-after flag, which both change with time. File imports have a rank weight; linking a shipped solution rebuilds the ledger; the weekly synthesis refreshes every score, the daily run only those it touched; ties end on the creation date, and a newly ranked sibling takes its score position.
- A proposed creation has a lifecycle: a `proposed` page whose evidence stays unattached and listed on the Changes row, attached when the squad accepts (the page becomes candidate or active), archived when it rejects; a need with a pending or rejected proposal is not proposed again every day. A candidate that reaches two accounts becomes active through a recorded `activate` change, and reframing is an earned type like renaming.
- A merge moves everything, not only the evidence: sub-opportunities, solutions and their assumptions, the outcome link and the signal mapping follow the survivor, and the undo moves them back. Each opportunity keeps a Summary (one line and two verbatims) so the tree summary that every run and the extractor read is stored, never rebuilt from the evidence base. The run log records Started at, Duration and the Recap.
- The daily run opens its run log entry first (so evidence and changes link to it and an interrupted run leaves a trace) and applies the squad's decisions before attaching anything; decisions made in Notion are fully recorded (Decided on filled, a correction for every rejection or edit). The weekly synthesis applies decisions first and ranks after its structural changes. Batches are sized by text (about 40,000 tokens), not by item count; the duplicate and already-ingested checks are one read per batch, not one per piece; the unattached backlog grouped into proposals is limited to 8 weeks; "a few", "notably" and "unusually large" have numbers; the signal window is 90 days; Freshness asked on is cleared by the run; the extractor returns the contact.
